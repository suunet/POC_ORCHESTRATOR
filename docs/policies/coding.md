# コーディング規約

## 前提

- 実装は`docs/design.md`に従う。設計に書かれていないこと、設計どおりに作れないことは、作らずに止めて相談する
- 標準ライブラリだけで作る。設定と定義は JSON で書き、検証は Go の構造体で行う
- Go の版は`go.mod`の`go`と`toolchain`の行で固定する

## パッケージ

- コマンドの入口は`cmd/gateflow/`。ここには引数の解釈と出力だけを書き、処理は`internal/`に置く
- `internal/`のパッケージは設計の構成図のとおりに分ける。新しいパッケージが必要なら、設計を更新してから作る
- パッケージの先頭のコメントに、そのパッケージが何をするかを1文で書く

## エラーと出力

- エラーは戻り値で返し、呼び出し側の文脈を足すときは`fmt.Errorf("...: %w", err)`で包む
- 利用者に見せるメッセージとコメントは日本語で書く
- 検査の誤りは最初の1件で止めず、まとめて返す
- 終了コードは、成功が0、検査に不合格が1、使い方や設定の誤りが2

## テスト

- テストを先に書き、失敗することを確かめてから実装する
- テストはコードと同じディレクトリに置き、パッケージは`<名前>_test`にして公開されたものだけを使う
- ファイルを使うテストは`t.TempDir()`の中で完結させる
- 外部のコマンド（docker、AIのCLI）はテストで実行しない。差し替えられる形にしておく

## 秘密情報

- 環境変数やトークンを読み書きするコードは、設計の「社内方針と構造による担保」に沿っているかを確かめてから書く

## コミット

- コミットメッセージは`<種類>(<マイルストーン>): <要約>`の形にする（例：`feat(M0): ID整合チェックを追加`）。種類は feat・fix・docs・test・refactor・chore
- pushとPRの作成は人が行う
