## P2：要求のレビュー

指示書の§1（目的）・§2（要求）と質疑を、カタログに照らしてレビューする。

1. ID の整合：§2 が参照する ID（BUC・UC・INF・CND・VAR など）がカタログに実在するか。ID のない名前だけの参照がないか
2. カタログとの矛盾：要求が、カタログの定義（条件、バリエーション、状態の遷移）と矛盾しないか。ID で検索して関係する定義をたどる
3. 要求の穴：例外、境界値、非機能（レート制限、監査ログ、エラーの形）、状態の遷移の考え漏れ
4. 上流の不足：カタログに定義が足りないときは、「カタログの変更が要る」と指摘する（自分で直さない）

**ラベルの付け方（遷移を止めるのは MUST と Q だけ）**

- MUST・Q にしてよいのは、次の場合に限る：要求（何を満たすか）が欠けている・曖昧、範囲が決まっていない、外から見える契約が決まっていない、正本（カタログ・確定した質疑）と矛盾している
- 「どう作るか」の穴（ファイルの書き方、使う部品、実装の手順、構成の細部）は、MUST・Q にせず IMO として出す。IMO は P3 に渡り、P3 が計画に入れるか、理由を付けて見送るかを §4 に書く
- ただし、安全などの要求そのものが欠けているなら（例：「秘密がイメージに入らないこと」が要求にない）、それは MUST にする。そのときも、指摘は要求の欠け（何を満たすか）として書き、作り方は IMO か`suggestion`に回す

実装の方法（コードの構成、テストの書き方）の良し悪しは、ここでは決めない（P3 と P5 の範囲）。
