## P2 の裁定

`/in/review.json`の BJ の指摘のうち MUST と Q、および BJ の質問（questions）を、1件ずつ裁定する。同じ内容の指摘と質問は1件に束ねる（findings と questions に番号を並べる）。

### 1. 人へ回す基準を先に当てる

次のどれかに当たるものは、決定者を human にし、当たる基準と人への質問（背景、番号付きの選択肢、推奨）を書く。

1. contract：外から見える契約の新設や変更（API の形、ヘッダー、ステータス、エラーの本文など）。契約の ID の一覧に挙がった ID に触れるものは、すべてこれに当たる
2. scope：範囲の変更（何を入れて何を外すか。ログを出すか出さないか、どの経路に適用するかも含む）
3. new-requirement：正本にも規約にも根拠のない、新しい要求
4. overturn：人が下した決定を覆すこと（質疑の決定者が人の回答と食い違う結論）
5. ambiguous：根拠を1つに絞れないとき（候補が0か、2つ以上で食い違う）

`/in/forced.json`に挙がった指摘は、必ず human にする。

### 2. 当たらないものだけを裁定する

根拠を、このチケットの確定した質疑（`/in/questions.md`）→ カタログ（`/work/.docs/design/`）→ 規約 → 公開の規格の順に探し、結論を支える根拠をちょうど1つ選ぶ。

- 根拠の書き方：question は Q 番号、catalog は ID、policy はリポジトリの中のパスと行（例：`.docs/operations/policies/coding.md:18`）、standard は規格の名前と節
- 規格は記憶による。版や細部に自信がなければ ambiguous として人へ回す
- 裁定の文（answer）は、質疑の回答として残る。結論と、根拠からそう決まる理由を書く

### 3. 裁定を反映する

- 指示書の §2 に直しが要るなら、裁定を反映した §2 の本文の全文を section2 に書く（見出しの行は含めない。要求の結論を1行ずつ書き、具体は Q 番号で参照する。既存の行を落とさない）
- カタログに直しが要るなら、作業ツリーの`.docs/design/`の下を直し、その裁定の edits に直した ID を挙げる。契約の ID には触れない
- 人へ回す裁定に関係するカタログは直さない

### 4. 結果

人へ回す裁定が1件でもあれば outcome は escalated、なければ resolved。MUST と Q の指摘と BJ の質問は、どれもちょうど1件の裁定に入れる。
