## P3：実装の準備

指示書の§1・§2、確定した質疑、カタログを読み、P5 の計画を作る。

1. 影響の範囲を調べる：§2 の ID で、カタログ、ユースケースの詳細、コードを検索する。結果を`current`（§3 変更前の現状）に書く
2. 方針を決め、`plan`（§4.1）に書く。カタログやコードの構成は規約に従う
3. 指示書の項目の「種別」を確かめる。種別が**実装**なら：ユースケースの詳細（`.docs/design/uc/UC-NNN.md`）を作るか更新し、受入条件の節に受入条件を`UC-NNN-AC-NN`の形で発番する。ひな形は`/in/templates/uc.md`。既にある受入条件の ID は変えない。受入条件を`acceptance`（§4.2）に、受入条件ごとのシナリオテストと、入力の検査などの単体テストを`testCases`（§4.3）に書く
4. 種別が**基盤**なら：受入条件は発番せず、`acceptance`は書かない。意味のあるテストが書けるとき（Go のコードを変えるときなど）だけ`testCases`に書く（0件でよい）。gateflow の中で確かめられない動作（コンテナの起動など）は、`hostCheck`（§4.5 ホストでの確かめ）に書く。基盤なら`hostCheck`は必須
5. `hostCheck`の書き方：`review`には、ホストで動かす前にコードレビューで読むファイルと、ホストに影響する設定（ホストのフォルダを繋ぐ設定、特権での実行、外へ公開するポート）が想定のとおりかを書く。`steps`には、コードレビューが通ってから行う手順を順に書き、手順ごとに何を見れば合格か（`pass`）を書く。種別が実装でも、gateflow の中で確かめられない動作があれば書いてよい
6. 設定ファイルに特定の文字が書いてあるかを確かめるだけのテストは作らない（書いた内容をもう一度読むだけで、動くかを確かめないため）
7. P5 で更新してよい文書（このステップで作った・更新したユースケースの詳細を含む）を`sheets`（§4.4）に書く
8. 業務の判断が要ること、値が決められないことは推測で埋めず、`questions`と`unfilled`に書いて`needs_answer`で終える

このステップで変えてよいのは、カタログ（`.docs/design/`）だけ。コードとテストは書かない（P5 で書く）。gateflow がこのステップの変更をコミットし、§3・§4 を指示書に書く。
